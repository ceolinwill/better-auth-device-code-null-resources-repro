# Better Auth: `POST /device/code` returns 500 on Prisma when no `resource` is requested

With `oauthProvider()` + `oauthDeviceAuthorization()` from `@better-auth/oauth-provider` and the Prisma adapter on PostgreSQL, a device authorization request that doesn't name a `resource` fails with a 500. The plugin writes `resources: null` to the `deviceCode` model, and Prisma rejects `null` for a scalar list column. The column is the `resources String[]` that Better Auth's own `npx auth generate` puts in the Prisma schema, so a project that follows the docs hits it on the first device login.

Reported in [better-auth/better-auth#11933](https://github.com/better-auth/better-auth/issues/11933) ([reproduction comment](https://github.com/better-auth/better-auth/issues/11933#issuecomment-6785016847)).

## Reproduction

Needs Node 24 and a local PostgreSQL. The script connects to `postgresql://postgres:postgres@localhost:5432/better_auth_device_code_repro` by default; set `DATABASE_URL` to use another server or user. `prisma db push` creates the database if it doesn't exist.

```sh
# Any PostgreSQL works, for example:
# docker run --rm -d -p 5432:5432 -e POSTGRES_PASSWORD=postgres postgres:18

npm install
npm run repro
# or: DATABASE_URL=postgresql://user:password@localhost:5432/better_auth_device_code_repro npm run repro
```

`npm run repro` pushes the committed schema, generates the Prisma client, signs up a user, registers a public client for the device code grant, and sends `POST /api/auth/device/code` with `client_id` and `scope=openid` and no `resource`.

`prisma/schema.prisma` was generated by Better Auth's CLI from `src/auth.ts` (`npm run generate-schema`, which runs `auth generate`). Its `deviceCode` model has:

```prisma
model DeviceCode {
  ...
  resources       String[]
  oauthClientId   String?
  ...
}
```

## Expected

`200` with a `device_code` and `user_code`. A request without `resource` is valid ([RFC 8707](https://datatracker.ietf.org/doc/html/rfc8707) makes it optional), so the device code should be saved with no resources, by leaving the field out (Prisma stores `[]`).

## Actual

`500`. In `@better-auth/oauth-provider`, `oauthDeviceAuthorization()` declares the field as `deviceCodeSchemaFields.resources: { type: "string[]", required: false }`, and `authorizeRequest` returns:

```js
deviceCodeFields: {
  oauthClientId: authenticated.clientId,
  resources: toResourceList(resource) ?? null,
},
```

(`packages/oauth-provider/src/device-code.ts`, `dist/index.mjs:171` in 1.7.20). The adapter factory passes the `null` through, and Prisma rejects it because a list column can't be `null`. Returning `undefined` instead of `null` fixes it, which is what [#11945](https://github.com/better-auth/better-auth/pull/11945) does on `next`. The same line is on `main`, which ships the device grant in 1.7.x.

## Environment

- `better-auth`, `@better-auth/oauth-provider`, `@better-auth/prisma-adapter`, `auth` (CLI): 1.7.20 (latest). Also fails on 1.8.0-beta.7 with all four packages on that version and the schema regenerated by its CLI.
- `prisma`, `@prisma/client`, `@prisma/adapter-pg`: 7.10.1
- PostgreSQL 18, Node 24.22.0, npm 11.19.1, macOS
